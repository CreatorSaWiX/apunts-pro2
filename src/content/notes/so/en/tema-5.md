## 5.1 Fundamentals and multiprogramming

To execute a program, its instructions and data must reside in RAM:
* **Program Counter (PC)**: CPU register holding the address of the next instruction to execute.
* **Instructions**: Jumps (`jmp`, `call`) and memory accesses (`mov`) reference target addresses.

Modern systems are **multiprogrammed** (they keep several processes simultaneously in RAM to switch the CPU without loading from disk on every context switch). This imposes **3 challenges on the OS**:

1. **Protection**: No process may access the memory of other processes or that of the Kernel.
2. **Dynamic allocation**: The OS places the process in available free physical memory (which varies on each execution).
3. **Address translation**: Code addresses must be translated into real physical memory locations.

### Logical addresses vs physical addresses

:::addrspaceviz
:::

* **Logical or virtual address (`@L`)**: The address generated by the compiler and referenced by the program during execution. Each process has its own isolated address space (starting from `0`), believing it has all of memory to itself without knowing which physical position it will occupy.
* **Physical or real address (`@F`)**: The actual, tangible position inside the RAM memory chips where data and instructions are stored. The process never has direct access to it; it is managed by the operating system, and the MMU is responsible for translating each `@L` to its `@F`.

## 5.2 Hardware support: MMU, page table, and TLB

Address translation is performed **at runtime directly by hardware (HW)** so as not to penalize CPU speed.

### The MMU (*Memory Management Unit*)
Physical component of the CPU located between the execution unit and the memory bus:

:::mmuviz
:::

1. The CPU emits a **logical address (`@L`)**.
2. The MMU attempts to translate it into a **physical address (`@F`)**.
3. **Valid access**: If the address exists and has appropriate permissions (read `r`, write `w`, execute `x`), the MMU sends `@F` to the RAM memory bus.
4. **Invalid access**: If the address does not belong to the process or violates permissions, the MMU triggers a **hardware exception** (*trap*). The Kernel handles it (usually sending `SIGSEGV` to the process).

### The Page Table (PT)
Kernel data structure (one per process) describing the memory mapping:

* The logical address is split into two parts:
  * **Page ($p$)**: Identifier of the logical page.
  * **Offset ($d$)**: Exact position within the page (remains identical in the physical address).
* Each entry (*PTE*) contains:
  * **Present/valid bit**: `1` if the page is in RAM; `0` if it is on disk/swap.
  * **Permissions**: Read (`r`), write (`w`), and execute (`x`) bits.
  * **Modified bit (*dirty bit*)**: Set to `1` by the CPU if it has been written to.
  * **Physical frame ($f$)**: Frame number in RAM where it is located.

:::pagetableviz
:::

> **Context switch:**  
> The base address of each process's PT is stored in its **PCB**. When switching processes, the Kernel loads this base address into the CPU control register (`%cr3` on x86). From that cycle onward, the MMU translates according to the new process's PT.

### The TLB (*Translation Lookaside Buffer*)
High-speed associative cache inside the CPU itself to accelerate translations:
* **TLB Hit**: The translation $p \rightarrow f$ is in the TLB; immediate resolution without accessing RAM.
* **TLB Miss**: The translation is not there; the MMU consults the PT in RAM, updates the TLB, and accesses the data.
* **Context switch**: The TLB is invalidated because it belongs to the previous process's address space.

:::tlbviz
:::

## 5.3 Loading an executable and anatomy of the logical space

When calling `exec`, the Kernel reads the **ELF** binary and builds its logical regions in the address space:

### 1. Memory regions and ELF sections (`objdump -h`)

:::memlayoutviz
:::

| Region / ELF Section | Permissions in `maps` | What does it contain? |
| :--- | :---: | :--- |
| **`.text`** (Code) | `r-xp` | Executable instructions (read-only for protection). |
| **`.rodata`** (Constants) | `r--p` | Constants and string literals. |
| **`.data`** and **`.bss`** (Globals) | `rw-p` | Global/static variables (uninitialized `.bss` takes 0 B on disk; the OS zero-fills it). |
| **`[heap]`** | `rw-p` | Dynamic memory (`sbrk`/`malloc`). Grows toward high addresses ($\uparrow$). |
| **`[stack]`** | `rw-p` | Local variables and stack frames. Grows toward low addresses ($\downarrow$). |

* **Address 0 (`NULL`)**: Intentionally unmapped page; dereferencing `NULL` causes an immediate `SIGSEGV`.

### 2. Live inspection with `/proc/[PID]/maps`

:::shellviz{command="cat /proc/self/maps" suggestions="cat /proc/self/maps,cat /proc/self/status,cat /proc/self/limits,ls -l /proc/self" title="Terminal — Process virtual memory map (/proc/self/maps)"}
:::

* **Format of each line**: `[address range] [permissions] [offset] [device] [inode] [label]`
* **`p` (*Private*) vs `s` (*Shared*)**: `p` indicates a private region with *Copy-On-Write*; `s` indicates true shared memory between processes.
* **Key practical details**:
  * **`[heap]` does not appear in `maps`** until the process requests dynamic memory (`sbrk`/`malloc`).
  * **Dynamic libraries (`libc.so`)**: Mapped in the intermediate region (*mmap*).
  * **`[vvar]` and `[vdso]`**: Kernel pages mapped into user space to accelerate frequent calls (e.g., `gettimeofday`) without a context switch.

## 5.4 Physical allocation: Paging

* **Page**: Fixed-size logical block that is a power of 2 (standard: **4096 bytes = 4 KB**).
* **Frame**: Physical block in RAM of the same size (4 KB).
* **Non-contiguous allocation**: A process's pages are distributed across scattered free frames; the PT maintains logical continuity.
* **Per-region isolation**: Each logical region (code, data, heap, stack, mmap) occupies separate pages: two different regions **never share the same physical frame**.

:::pagingviz
:::

### Internal vs external fragmentation

:::fragviz
:::

| Type | What is it? | In Paging? | Calculation |
| :--- | :--- | :---: | :--- |
| **Internal** | Allocated but unused memory because the region is not a multiple of 4096 B. | **YES** | A 2400 B region in a 4096 B page $\rightarrow$ wastes $4096 - 2400 = 1696$ B in the last frame. |
| **External** | Scattered free holes that cannot satisfy a large contiguous request. | **NO** | Any free 4 KB frame works for any page. |

## 5.5 Dynamic memory: `sbrk` vs `malloc`

### 1. System call: `sbrk()`
Modifies the heap limit (*break pointer*):

```c
#include <unistd.h>
void *sbrk(intptr_t increment);
```
* `sbrk(0)`: Returns the current address of the heap limit.
* `sbrk(N)`: Increases the heap by $N$ bytes and returns the previous address.
* `sbrk(-N)`: Shrinks the heap by $N$ bytes.

:::sbrkviz
:::

> **Kernel granularity:**  
> Even if you request `sbrk(100)`, the Kernel allocates full **4096-byte** physical frames. The effective limit in `/proc/[PID]/maps` is always rounded up to the next page multiple.

### 2. C library (`<stdlib.h>`): `malloc()`, `realloc()`, and `free()`
Requesting memory with `sbrk()` directly is inefficient (many system calls and inability to free intermediate holes). `libc` manages this in user space:

* **`malloc(size)`** / **`calloc(n, size)`** *(zero-initialized)*: Reserves a block on the heap. `malloc(64)` usually requests a large chunk from the Kernel (e.g., 132 KB via `sbrk`) to hand out pieces; for very large requests (> ~128 KB), it uses **`mmap()`** outside the heap.
* **`realloc(ptr, new_size)`**: Resizes a previously allocated block (expands it *in place* if space is available, or moves it to a new address, copying the contents and freeing the old one).
* **`free(ptr)`**: Marks the block as reusable within `libc`. It usually **does not reduce the heap limit (`sbrk`)** for small blocks (it does call `munmap` if it came from `mmap`).

### `SIGSEGV`: `sbrk` vs `malloc` out of bounds
* With `char *p = sbrk(4096);`, accessing `p[4100] = 'a';` falls outside the allocated page $\rightarrow$ the MMU has no translation $\rightarrow$ **`SIGSEGV`**.
* With `char *p = malloc(4096);`, accessing `p[4100] = 'a';` may not crash because the library requested excess memory and position 4100 lies within a page already valid for the MMU (even though it is a serious bug in the code).

:::mallocviz
:::

## 5.6 Mapping outside the heap: `mmap` and `munmap`

```c
#include <sys/mman.h>
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int munmap(void *addr, size_t length);
```

* `addr`: Suggested logical address (`NULL` so the Kernel chooses a free address).
* `length`: Size in bytes of the region (the Kernel reserves full 4 KB pages).
* `prot` (access permissions; combined with `|`):
  * **`PROT_READ`**: Allows reading from the region.
  * **`PROT_WRITE`**: Allows writing to it (without this permission, writing triggers `SIGSEGV`).
  * **`PROT_EXEC`**: Allows executing instructions from it.
  * **`PROT_NONE`**: No access permissions (blocked page, useful as a guard/sentinel).
* `flags` (behavior; requires **`MAP_PRIVATE`** or **`MAP_SHARED`**, combinable with other flags):
  * **`MAP_PRIVATE`**: Private changes (via COW). Files are not modified and other processes do not see them.
  * **`MAP_SHARED`**: Changes visible to other processes and reflected in the file.
  * **`MAP_ANONYMOUS`**: Reserves pure memory with no associated file (`fd = -1`, `offset = 0`).
* `fd` and `offset`: Descriptor of the file to map and starting offset within the file (page-aligned).
* **Error handling**: On failure, `mmap` returns **`MAP_FAILED`** (not `NULL`!).

:::mmapviz
:::

### Pattern 1: Anonymous memory (`MAP_ANONYMOUS`)
Reserves memory directly outside the heap (`fd = -1`, `offset = 0`):
* With **`MAP_PRIVATE | MAP_ANONYMOUS`**: private process buffer (alternative to `malloc`), freed with `munmap(ptr, size)`.
* With **`MAP_SHARED | MAP_ANONYMOUS`**: shared memory between related processes after a `fork()`:

```c
int *counter = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
                    MAP_SHARED | MAP_ANONYMOUS, -1, 0);
if (counter == MAP_FAILED) { perror("mmap"); exit(1); }

*counter = 100;
if (fork() == 0) {
    *counter = 42; // The child modifies the shared physical value
    exit(0);
}
waitpid(-1, NULL, 0);
// The parent reads 42: they share the same physical frame!
munmap(counter, sizeof(int));
```

### Pattern 2: Memory-mapped files
Allows reading and writing files via pointers, without `read()` or `write()`:

```c
int fd = open("data.bin", O_RDWR);
char *data = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

data[0] = 'X'; // Transparently modifies the file on disk

munmap(data, 4096);
close(fd);
```

## 5.7 Key operating system optimizations

### 1. Demand paging
On `exec`, the OS does not copy the entire executable file into RAM:
* It creates the regions in the PCB and marks the pages as **non-resident** (present bit = `0`).
* When the CPU executes an instruction from an unloaded page, the MMU generates a page fault.
* The Kernel reads only that 4 KB block from disk, places it in a free frame, and resumes the process.
* **Static binaries (`-static`)**: Allows running large programs without loading library code that is never called.

:::demandpagingviz
:::

### 2. Shared dynamic libraries (`.so`)

:::sharedlibviz
:::

* Code from common libraries like `libc.so` is loaded **only once into RAM** (saving disk and physical memory).
* Processes map it as private read/execute (`r-xp` in `maps`), but as long as it is not written to, the MMU points to the **same shared physical frames**.
* Each process keeps its own private copy of data (`.data`, `rw-p`).

### 3. Copy-On-Write (COW)
Eliminates the cost of duplicating all physical memory on `fork()`:

1. **On creation (`fork`)**: Parent and child share the same physical frames in RAM. All PT entries are marked as **read-only (`r--` or `r-x`)**.
2. **On write**: When a process attempts to write (`ret = fork()` on the stack or `*p = 'A'`):
   * The MMU detects an unpermitted write attempt and raises an exception.
   * The Kernel checks in the PCB that the process has write permission (it is a COW region).
   * The Kernel allocates a **new 4 KB physical frame**, copies the original frame's contents into it, updates the writing process's PT with `rw-` permission, and restarts the instruction.
3. **Unmodified pages**: Code and read-only data remain **shared indefinitely**.
4. **Mutation with `execlp()`**: If the child mutates, its logical and physical space is completely destroyed and recreated from scratch; it stops sharing frames with the parent.

:::cowviz
:::

## 5.8 Virtual memory, page faults, and thrashing

Allows the sum of processes' logical address spaces to exceed the physical capacity of RAM by using disk as secondary storage (**Swap area**).

* **Resident page**: Has a physical frame assigned in RAM (present bit = 1).
* **Non-resident page**: Stored on disk or in the swap area (present bit = 0).

### Page fault sequence

:::pagefaultviz
:::

1. The CPU attempts to access a logical address with present bit = `0`.
2. The MMU raises a page fault exception.
3. The Kernel puts the process into the **`BLOCKED`** state.
4. The Kernel looks for a free frame in RAM:
   * If none is free, the **replacement algorithm** (LRU) chooses a **victim page**.
   * If the victim has been modified (*dirty bit* = 1), it is written to Swap; otherwise, it is discarded. Its PT entry becomes present = `0`.
5. The Kernel reads the required page from Swap or the executable and copies it into the free frame.
6. It updates the process's PT (assigns frame and present bit = `1`).
7. The process transitions to **`READY`**.
8. Upon receiving the CPU, the instruction that failed is **restarted from the beginning** and executes successfully.

### Types of faults and page replacement

:::pagereplaceviz
:::

* **MMU exception $\neq$ always `SIGSEGV`**: When translation fails, the Kernel consults the PCB. It only sends `SIGSEGV` if the address does not belong to the process or violates permissions; if it is *COW* or a *page fault*, it resolves it transparently and restarts the instruction.
* **Minor vs Major Page Fault**:
  * **Minor**: The page is already in RAM (e.g., *COW* copy or data already present in cache); **no disk access**.
  * **Major**: Must fetch the page from disk or Swap; blocks the process until the read completes.
* **Basic replacement algorithms** (to choose the victim page when RAM is full):
  * **FIFO**: Evicts the page that entered earliest.
  * **LRU (*Least Recently Used*)**: Evicts the one that has gone unused the longest (very good efficiency, expensive to implement in pure hardware).
  * **Clock (*Second Chance*)**: Efficient approximation of LRU using an access bit set to `1` by the MMU on each read/write.

### Thrashing

:::thrashingviz
:::

Occurs when the sum of working sets (minimum number of pages each process needs active) exceeds available physical memory:
* Processes continuously steal frames from one another.
* The CPU spends 99% of its time waiting for I/O transfers with Swap, and throughput drops to zero.
* **OS solution**: Reduces the degree of multiprogramming by swapping entire processes out to Swap (**swapped-out state**) until the remaining ones finish their work.
